三个核心规则设计

以下三条是我在文档化过程中主要推演和论证的规则，均可接受深挖追问。

① 库存扣减三档漏斗

加购宽松（仅提示不真扣）→ 结算较严格（红字提示+刷新）→ 支付真实扣减。 加购即扣库存会导致库存被占死（用户随手加后放置不买）与锁竞争（热门商品多人同时加购）。 且区分：彻底无货→拦截（确定），库存紧张→提示放行（可能是并发瞬时数据，不确定）。

自省：初版设计为"库存紧张时静默加购"，回头看应改为有提示放行——因为拦截用户付出时间成本后发现无法购买，体验更差。

② 积分抵扣多批次分配算法

两层独立排序：批次间按适用范围"窄→宽"、批次内按过期时间"早→晚"，再以商品价格权重分配。 不用"按积分比例平均分"，因为会产生 0 元商品，而 0 元商品退款极难处理。 明确不找零：只消耗等额积分，剩余积分保留在账户。

硬证据（同一算例对比）：窄范围优先消耗 6000 分；宽范围优先仅消耗 4875 分，差 1125 分。

③ 订单与多包裹状态映射

一单可拆多包裹（供应链按商品维度拆单）。订单状态 = MIN(所有包裹状态)，优先级：待发货 < 运输中 < 已签收。 理由是不能让用户误判——若显示"已完成"但仍有包裹在途，必然产生投诉。 "部分发货/部分签收"是中间态，不作为订单主状态入库，仅在详情页由前端按包裹实时推导。

自省：自动确认收货的 15 天是拍的经验值，应做成可配置项并用历史数据校准，不该硬编码进 PRD。

文档产出

采用三段式业务逻辑清单结构：功能用例表 + 关键字段数据来源 + 业务逻辑增强。中间那段把每个字段归属到具体后台系统，研发与测试无需猜测。

版本迭代主线

「用户选积分的单位」越来越细：单类型 → 单批次 → 同组多批次叠加。而底层三原则从V0.2 到 V0.7 从未变过：窄范围优先、快过期优先、按价格权重分配。
